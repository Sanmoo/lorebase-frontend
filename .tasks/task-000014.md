## Problema

Na aba Social > Profile > Lists, o frontend chama `GET /profiles/{userId}/lists?limit=20` uma única vez e agrupa localmente os primeiros 20 itens globais por status. Com isso, se a primeira página global tiver poucos itens `PLAN_TO_WATCH`, a seção **Quero ver** mostra itens ausentes mesmo quando há mais conteúdos públicos nessa lista.

## Contexto

Investigação relacionada à task backend `lorebase-backend:task-000005` mostrou que o backend já suporta filtros `status`, `mediaType`, `limit` e `cursor` no endpoint `GET /profiles/{userId}/lists`. O frontend não usa esses filtros na tela de perfil social.

Arquivos relevantes:

- `lib/features/social/viewmodels/social_profile_viewmodel.dart`
- `lib/features/social/data/repositories/social_repository.dart`
- `lib/features/social/pages/social_profile_page.dart`
- `lib/features/social/widgets/public_media_list_section.dart`

## Proposta

Atualizar a aba Lists do perfil social para carregar listas públicas por seção/status, em vez de depender de uma única página global. Inicialmente carregar pelo menos:

- `PLAN_TO_WATCH` → Quero ver
- `WATCHING` → Assistindo
- `COMPLETED` → Concluído
- `DROPPED` → Abandonado

Cada chamada deve usar `getPublicLists(userId, status: <status>, limit: ...)`.

## Critérios de aceite

- [ ] A aba Lists não depende mais apenas de `GET /profiles/{userId}/lists?limit=20` sem status para montar todas as seções.
- [ ] A seção **Quero ver** é alimentada por uma chamada filtrada com `status=PLAN_TO_WATCH`.
- [ ] A UI mantém agrupamento/ordem esperada das seções sociais.
- [ ] Erro em uma seção não deve derrubar o perfil inteiro, preferencialmente degradando só a seção afetada.
- [ ] Testes cobrem que `getPublicLists` é chamado com status por seção e que itens `PLAN_TO_WATCH` aparecem mesmo quando não estariam garantidos pela primeira página global.
- [ ] Rodar `flutter test` relevante e `make analyze` ou justificar se não for possível.
